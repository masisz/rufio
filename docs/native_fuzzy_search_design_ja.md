# 内蔵曖昧検索の設計（rufio 1.6.0）

ブランチ: `v1.6.0`
ステータス: Phase 1〜5 実装済み。fzf との比較で見つかった性能差も改善済み（末尾の「性能改善」）。

## 目的

外部 fzf に依存せず、ファイル名・パスを順序を保った飛び飛び一致で検索する。
絞り込み速度は fzf と同等以上、再表示は候補キャッシュによる短縮を目指す。
現時点では性能目標であり、Zig 化だけで高速化を保証しない。

## 責務

- Zig: 候補を保持し、照合・スコア計算・上位 K 件の選別を行う。
- Ruby: 入力、検索世代の管理、Screen / Renderer による表示、選択後の操作。
- Ruby フォールバック: 同じ検索仕様を持ち、ライブラリがない・古い場合にも利用できる。
- 既存 `core_files_create` を候補列挙に利用し、入力ごとに走査し直さない。

## 検索仕様（Phase 1）

- UTF-8 のコードポイント単位の部分列一致。ASCII の英字だけ大文字小文字を無視する。
  日本語はそのまま照合する。Unicode 正規化・非 ASCII の case folding は初期対象外。
- 1 文字の一致 +16、パスの最後の区切り以降 +8、単語境界 +8、連続一致 +24。
  先頭からの距離と一致間の隙間は 1 文字につき -1、候補の文字数を減点し、全体一致は +64。
  境界は先頭、`/`・`\\`・`_`・`-`・`.`・空白の直後、小文字から ASCII 大文字への遷移。
- 動的計画法で最も高いスコアの一致を選ぶ。同スコアでは末尾の一致位置が早い方を選び、
  同一末尾への遷移が同点なら直前の一致位置が早い方を選ぶ。
- 候補の順位はスコア降順、同点は追加時の ID 順。空クエリでは追加順。
- 位置は元の UTF-8 文字の先頭バイトオフセットとして返す。描画時に表示幅へ変換する。
- 候補は追加後に保持し、再検索で再転送しない。上位 K 件だけを返し、総一致件数は別に保持する。
- 不正 UTF-8 / NUL を含む文字列は明示的に拒否する。クエリは 1,024 バイト、
  候補は 65,536 バイト、返却件数は 10,000 件を上限とする。
  ファイル走査側は表示用文字列を scrub し、実際に開くパスは別に保持する。

## FFI と寿命

`core_fuzzy_create` / `add` / `query` / `results` / `destroy` を独立した API 群として追加する。
候補は NUL 区切りの UTF-8 でまとめて追加し、ID は 0 からの追加順とする。
結果は little-endian のバイナリで、先頭に総一致件数 u64 と返却件数 u32、
各レコードに ID u64、スコア i64、一致位置数 u32、位置 u32 配列を格納する。
結果ポインタは次の query / destroy まで有効。Ruby はその場でコピーする。
同じハンドルへの呼び出しは直列化し、close は冪等にする。古いライブラリの関数不足は
他の検索・ZIP API の利用可否に影響させない。

候補ごとの FFI 呼び出しと全件ソートを避け、Zig では最悪候補を根にしたヒープで
上位 K 件を保持する。スコアは O(候補文字数 × クエリ文字数)、作業領域は O(候補文字数)。
一致位置の復元用 O(候補文字数 × クエリ文字数) の領域は上位候補にのみ、一候補ずつ確保する。
スコア計算前に部分列として成立するかを O(候補文字数) で確認し、不一致を早期除外する。

## 実装段階

1. **検索コア**: Zig / Ruby 共通仕様、永続候補、top-K、一致位置、FFI、比較テスト、ベンチマーク。
2. **検索セッション（実装済み）**: 非同期走査、入力の集約、世代番号による古い結果破棄、キャンセル。
   単一の検索ワーカーでインデックスのハンドルを専有し、UI スレッドから destroy しない。
   走査は別のプロデューサーで実行し、受け渡しには容量制限を設ける。
   実測で長い query が問題なら、スコア走査中のキャンセルを追加する。
3. **操作の置き換え**: `s` / `/` を内蔵画面へ、`F` の rga 結果選択も共通画面へ接続する。
   `F` の本文検索には引き続き rga を使う。fzf のヘルスチェックと説明を除去する。
   既存の `fzf_search` アクション名はユーザー設定互換のため別名として維持する。
4. **再表示とプレビュー**: キャッシュを容量・有効期限で制限し、再走査による更新を可能にする。
   新規・削除・外部更新を考慮し、キャッシュ結果が常に最新とは表示しない。
   選択後のプレビューは非同期・サイズ制限付きとし、結果到着で選択 ID が動かないようにする。
5. **展開**: G のファイル名検索と f のフィルターへ適用を検討し、8 プラットフォームをビルド・検証する。

`s` の現行 find は隠しファイルを含む。G の除外拡張子を無条件に流用しない。
ディレクトリのシンボリックリンクは追わない。内蔵候補一覧では通常ファイルへのリンクも含める
（現行 `find . -type f` からの変更点）。Ruby / Zig の一覧で同じ扱いになることをテストする。
本文検索そのものの高速化と、fzf の検索式全体の互換性は本計画の対象外。

## 検証と計測

- 期待する順位・一致位置、日本語・空文字・重複・同点・追加後の再検索・解放をテストする。
- 同じ候補とクエリで Ruby / Zig の ID・スコア・位置・総件数を一致させる。
- Debug ビルドで安全性を検証し、速度は ReleaseFast で測る。
- 1 万・10 万・100 万候補を用意し、登録時間、検索中央値・p95、返却上限、メモリを測る。
- fzf 比較では同一候補入力を使い、起動・入力転送込みの時間と検索コア時間を区別する。
  初回ディスク走査、入力から描画まで、再表示、プレビューは UI 実装後に別途測る。
- ベンチマークは通常の単体テストから分離し、測定環境・件数・クエリ・試行数を記録する。

## Phase 2 の成果（2026-11-14）

### 非同期セッション

`Rufio::FuzzySearchSession` を追加した。1 回の検索画面に 1 セッションを割り当てる。
再利用するインデックスはセッション内だけで、画面の再表示キャッシュは Phase 4 の対象。

- `start` で走査と検索の 2 ワーカーを開始する。検索インデックスは検索ワーカー内で
  作成し、追加・照合・解放もそのワーカーだけで行う。
- `update_query` は最新の入力と世代番号を保存してすぐ戻る。実行中の検索が戻ったら
  中間の入力を飛ばして最新の入力を処理する。検索中に別の native query を重ねない。
- 世代の古い結果は公開時と `poll` 時に破棄する。入力変更時点で表示済み結果も消し、
  前の検索の結果を選択しないようにする。
- `poll` は最新のスナップショットを最大 1 個取り込む。`snapshot` は凍結済みで、
  クエリ・結果・総一致件数・登録件数・進行状態・エラーを同じ版として読める。
  結果は `{ id:, score:, positions:, entry: }`、entry は表示名 `text` と元の `path` 等を持つ。
- 走査から受け取る待機キューは最大 4 バッチ × 256 件。キューが満杯なら走査側を待たせる。
  検索ワーカーは一度に最大 4 バッチを取り込み、件数に比例して待機キューが膨らまない。
  インデックス本体とパスの登録件数にはまだ上限を設けていない。
- 候補追加だけで起きる再検索は既定で 50ms 間隔に集約する。入力変更と走査完了は
  この待ち時間を省く。ただし実行中の照合は完了を待つ。走査が一時停止していても
  待機期限で起きて部分結果を更新する。`refresh_interval` で間隔を変更できる。
- `scanning?` は未登録の候補バッチも含む。`searching?` は現在の入力・登録候補に
  対する結果更新の待機中も true になる。候補追加の集約中は、同じクエリの一つ前の
  部分結果を保持するため、総一致件数はまだ増え切っていないことがある。
- 走査エラーは最大 100 件保持し、読めたファイルの検索は続ける。
  検索ワーカーが失敗した場合は走査側も停止し、エラーを公開する。

### ファイル一覧

`Rufio::FuzzyFileSource` は既存の `core_files_create` を使い、未搭載・
`RUFIO_NATIVE_SEARCH=0`・`native: false` の場合は Ruby で走査する。
隠しファイルを含め、G モードの除外拡張子は持ち込まない。ファイル本文は開かない。
ディレクトリのリンクと壊れたリンクは候補にせず、通常ファイルへのリンクは含める。
表示名だけを UTF-8 に scrub し、元のパスは元のバイト列・エンコーディングのまま保持する。

`source:` に独自プロデューサーを渡すこともできる。実装する契約は
`each_batch(cancelled:, on_error:) { |batch| ... }`。
バッチの各項目は文字列、または `{ text: '表示名', path: '元のパス', line_number: 4 }` のような
Hash とする。メタデータの値は文字列・数値・Symbol・真偽値・nil に限り、文字列はコピーして
保持する。これにより Phase 3 の rga 結果選択にも同じセッションを利用できる。

### 終了と制約

`close` は停止通知を送り、待機キューと公開結果を破棄して戻る。
UI スレッドでは join・destroy・`Thread#kill` を呼ばない。
進行中の FFI 呼び出しやファイルシステム操作が戻った後、所有ワーカーが解放する。
ネイティブ走査は空バッチで待っている間も停止通知を確認できるよう、
`NativeContentSearch#each_batch(cancelled:)` に省略可能な停止判定を追加した。

アプリ終了等で完了を待つ場合は、`close` の後に `wait(timeout: 秒数)` を呼ぶ。
false は解放処理がまだ継続中であることを示す。`wait` 自体は停止要求ではなく、
close 前に呼ぶと次の入力を待つ検索ワーカーも待ち続ける。
独自 source はバッチ間で停止判定を確認する必要があり、ブロックした任意の I/O を
強制終了する仕組みは設けていない。照合途中の Zig キャンセルもまだ追加していない。

```ruby
session = Rufio::FuzzySearchSession.new(root: Dir.pwd).start
begin
  session.update_query('sctrl')
  loop do
    session.poll
    state = session.snapshot
    # 描画・選択処理には state.results と state.errors を渡す。
    break unless state.scanning || state.searching

    sleep 0.01
  end
ensure
  session.close
  session.wait(timeout: 1) # false の場合、所有ワーカーでの後処理は継続する。
end
```

## Phase 3 の成果（2026-11-15）

### 画面とキー

- `Rufio::FuzzyFinder` を追加した。G mode と同じく全画面で描画し、`TerminalUI#start_fuzzy_finder(session, title:) { |entry| ... }`
  で開く。1 回の表示に 1 つの `FuzzySearchSession` を割り当て、開くときに start、ESC・選択・G mode の起動で close する。
- 入力は G mode の矢印・SS3・CSI u の解釈を共有する（`TerminalUI#search_overlay_active?`）。
  文字キーはすべて検索語になり、`?` もヘルプではなく入力として扱う。Ctrl+J は `"\n"` と同じバイトなので Enter には使わない。
- 一致位置（UTF-8 先頭バイトオフセット）を表示桁へ変換してハイライトする。省略記号で切った行は省略記号を上書きしない。
- 候補の追加で順位が変わっても、選択中の候補 ID を追う。検索語を変えたときは先頭に戻す。
- 選択時のコールバックが `:needs_refresh` を返すと全画面を再描画する（外部エディタから戻った後）。
- 全画面ビューで結果が減ったときに前フレームの行が残る不具合があった（G mode も同じ）。
  `Screen#clear(mark_dirty: true)` で全行を Renderer の比較対象にして解消した。既定の `clear` の動作は変えていない。

### 操作の置き換え

- `s` / `/`: `SearchController#file_search` が現在のディレクトリを `FuzzyFileSource` で列挙する。
  選択したファイルは従来どおり `FileOpener#open_file` で開く。
- `F`: 入力ダイアログで検索語を受け取り、`RgaResultSource` が `rga --line-number --with-filename --no-heading --color never -- 語 .`
  の出力を 256 件ずつ流す。表示名は scrub し、パスは元のバイト列から組み立てる。
  停止判定は 50ms ごとに確認し、出力が止まった rga も終了させてから回収する。選択行は `open_file_with_line` で開く。
- アクション名を `file_search` / `file_search_alt` に変更した。ユーザー設定の `fzf_search` / `fzf_search_alt` は別名として
  受け付け、新しい名前と両方ある場合は新しい名前を優先する（`ConfigLoader::LEGACY_KEYBIND_ACTIONS`）。
- ヘルスチェックから fzf を除いた。プレビューは Phase 4 で追加するため、fzf の `--preview` 相当はまだない。

`rake native:build` で全 8 プラットフォームを再ビルドし、`rake native:check` と `make test`（Zig 単体テスト）を通した。

## Phase 4 の成果（2026-11-15）

### 再表示キャッシュ

`Rufio::FuzzyCandidateCache` を追加し、`SearchController` が 1 つ保持する。
`source_for(root)` はキャッシュがあれば再生用ソースと保存時刻を、なければ走査を記録するソースを返す。
記録は最後まで走査できたときだけ保存し、途中で閉じた・上限を超えた一覧は保存しない。

- 上限は合計 200,000 候補・4 ディレクトリ・保存から 300 秒。最近使ったものを残し、古いものから捨てる。
- 候補は「表示名 NUL パス NUL」を連結した 1 本のバイト列で持つ。パスが「ルート/表示名」と同じならパスを省略する。
  最初は 1 件ずつ Hash で保持したところ、168,530 件で約 110MiB 増えたため変更した。変更後は 13.8MiB。
  走査中も Hash を溜めず、届いた候補をその場で詰める。保持するのは text と path だけ。
- 再生は 256 件ずつ展開して流す。全件を先に展開すると最初の結果が 150〜390ms 遅れたため。
- インデックスはこれまでどおりセッションのワーカー専有で、再表示のたびに作り直す。
- キャッシュから表示したときはタイトルに `Cached 2m ago | Ctrl+R: Rescan` と出し、常に最新とは示さない。
  `Ctrl+R` はキャッシュを捨てて走査し直し、入力中の検索語を新しいセッションに引き継ぐ。
- 選択したファイルが消えていたら、選択時のコールバックが `:missing` を返す。
  `TerminalUI` は画面を閉じずに `File no longer exists` を表示する（`F` の結果も同じ）。
- rufio 自身のファイル操作でキャッシュを消す連携はまだない。有効期限と `Ctrl+R` で更新する。

### プレビュー

`Rufio::FuzzyPreviewLoader` を追加した。プレビューを有効にして開いた画面ごとに 1 つ作り、閉じるときに止める。

- 読み込みは 1 本のワーカーで行い、処理中に選択が変わったら、終わった後はその時点の最新の要求だけを読む。
  UI スレッドは待たない。close は停止を伝えるだけで、読み込み中のファイル操作が戻った後にワーカーが終わる。
- `FilePreview` を使うので 64 KiB・1 行 500 文字に制限される。行番号つき（`F`）は行番号 + 200 行（最大 2,000 行）を読む。
  直近 16 件の結果を再利用する。
- 幅 80 桁以上で右半分に表示し、タブは空白 4 つ、制御文字は空白に置き換える。`F` は一致行を中央付近に出して背景色で強調する。
  `UI_OPTIONS` の `preview_enabled: false` で無効にできる。
- 結果の到着で選択が動かないことを、順位が上がる候補を後から追加するテストで確認した（選択位置の追従は Phase 3 で実装）。

### 計測

macOS（Darwin 27.2）・arm64・同梱 ReleaseFast ライブラリ、`~/devs` 配下 168,530 ファイル。
`FuzzyFinder` を開いてから全候補の登録が終わるまでを、同じプロセスで 6 回連続で測った。

| 回 | 種類 | 最初の結果 | 全件の取り込み |
|---:|---|---:|---:|
| 1 | 走査 | 65ms | 1,718ms |
| 2〜6 | キャッシュ | 11〜17ms | 759〜1,051ms |

キャッシュからの全件取り込みの内訳は、展開約 140ms、インデックス登録約 390ms、セッション内のコピー約 250ms だった。
登録とコピーはキャッシュの有無にかかわらずかかる。インデックス自体を画面間で使い回すと
さらに短くできるが、ワーカー専有の寿命管理が複雑になるため今回は見送った。

### 検討と判断

`~/devs` 配下 168,551 ファイルで、従来の G のファイル名絞り込み（UI スレッドで毎キー全件の部分一致）と
同梱 Zig のあいまい照合（上位 1,000 件）を比べた。

| 検索語 | 部分一致（UI スレッド） | 一致数 | あいまい照合 | 一致数 |
|---|---:|---:|---:|---:|
| `s` | 38.0ms | 162,282 | 25.2ms | 162,282 |
| `sc` | 44.5ms | 13,354 | 38.0ms | 146,511 |
| `sctrl` | 47.3ms | 0 | 46.4ms | 41,502 |
| `search_controller` | 51.8ms | 3 | 21.5ms | 23 |

- **G のファイル名**: あいまい検索に切り替えた。一致数は増えるがスコア順に並ぶ。照合はバックグラウンドに移し、
  1 キーごとに UI スレッドを 40〜50ms 止めていた問題も解消する。本文検索はリテラルのまま。
- **f フィルター**: 変更しない。ディレクトリ一覧の並び順を保つことが目的で、件数も少なく性能上の問題がない。
  スコア順に並べ替えると一覧の見え方が変わるため。

### G のファイル名検索

- `GlobalSearch::FileNameSource` が既存の走査（Zig の `scan_files_natively` / Ruby の `scan_roots`）のイベントを
  候補バッチに変換し、`FuzzySearchSession`（上位 1,000 件）に流す。除外設定・ブックマーク名・skipped の数は従来どおり。
  停止要求は次のイベントで走査を打ち切り、Zig 走査は `each_batch(cancelled:)` で待機中も止まる。
  ファイル名検索では `Thread#kill` を使わない（本文検索の走査スレッドは従来どおり）。
- 候補の text はブックマークからの相対パス（scrub 済み）。メタデータに path・bookmark・relative_path を持つ。
- 検索語を変えると、新しい結果が届くまで一覧を空にして前の結果を選べないようにする。選択は候補 ID で追う。
- ハイライトは一致位置（バイトオフセット）を表示桁に変換して描く。

手元の 5 ブックマークでも動作を確認した。`~/devs` だけをブックマークにした計測では、走査 1,026ms（168,592 件）の後、
1 文字ずつ `sctrl` と入力したときの `handle_key` は 0.01〜0.02ms、結果の到着は 28〜79ms だった。

### キャッシュ上限の設定

`~/.config/rufio/config.rb` の `FUZZY_SEARCH_CACHE` で変更できる（`ConfigLoader.fuzzy_search_cache`）。

| キー | 既定値 | 上限 |
|---|---:|---:|
| `max_entries` | 200,000 | 1,000,000 |
| `max_roots` | 4 | 16 |
| `ttl`（秒） | 300 | 86,400 |

0 以上の整数だけを受け付け、上限を超える値は上限に丸め、それ以外は既定値に戻す。0 は無効化または即時期限切れ。
上限は Phase 1 で計測した 100 万候補までに合わせた。キャッシュは 1 ファイル約 86 バイト（168,530 件で 13.8MiB）なので、
上限いっぱいでも約 80MiB に収まる。設定は起動時に読み込む。

## fzf との比較と性能改善（2026-11-15）

### 比較方法

Apple M3（8 コア）、`~/devs` 配下 168,785 パス、fzf 0.74.5。fzf は画面表示版を `--listen` 付きで起動し、
HTTP の `change-query(...)` を送ってから状態の `query` が一致し `progress` が 100 になるまでを測った
（HTTP の往復は約 0.16ms）。`fzf --filter` は全一致行の出力に時間がかかり、照合の比較には使えなかった。
rufio は `FuzzySearch#query`（上位 1,000 件）を直接測った。いずれも中央値。

### 改善前に見つかった差

- 1 文字ずつ入力すると fzf は前回の結果から絞り込み、複数コアで照合する。rufio は毎回全件を 1 スレッドで照合していた。
- rufio の Zig インデックスは候補ごとに 1 文字 9 バイト（u21 文字・u32 位置・u8 ボーナス）を 3 つの別領域で持ち、
  候補 14MB に対して約 222MiB 増えていた。fzf はプロセス全体で約 44MB。

### 変更内容

1. **前回の結果から絞り込む**: 前回の検索語が新しい検索語の部分列なら、前回一致した ID と、その後に追加された候補だけを照合する。
   途中に文字を挿入した場合も成り立つ。空の検索語の後や、短くした・無関係な検索語は全件を照合する。
   Ruby フォールバックも同じ規則で絞り込み、`FuzzySearch#scanned`（Zig は `core_fuzzy_scanned`）で照合件数を確認できる。
   `core_fuzzy_scanned` がない古いライブラリでも他の API はそのまま使い、`scanned` は nil になる。
2. **複数スレッドの照合**: 照合対象が 16,384 件以上なら CPU 数（最大 16）のスレッドで、1,024 件ずつのチャンクを
   atomic なカウンタで取り合う。効率コアが遅くても他のスレッドが残りを処理する。各スレッドの上位 K 件をまとめて
   並べ直すので、結果は 1 スレッドと同じ。一致 ID はチャンク順に詰めるので昇順のまま。
   作業領域はスレッド開始前にすべて確保し、スレッド内では確保しない。スレッドを作れなかった分は他のスレッドが処理する。
3. **インデックスの縮小**: 候補は連結した UTF-8 と、開始位置（usize）・文字数（u32）だけを持つ。
   まず生のバイト列で部分列判定をし（ASCII の検索語なら UTF-8 の復号も不要）、通ったものだけ
   文字・ボーナスをスレッドごとの作業領域に復号して DP を行う。一致位置は上位候補の出力時だけ復号する。
4. **登録の高速化**: セッションは凍結済みの候補（文字列も凍結・UTF-8 として正しい）をコピーせずに保持する。
   ファイル一覧・rga・G のソースは凍結した候補を出す。`FuzzySearch#add` は UTF-8 の文字列を複製しない。

検証: Zig の単体テスト 8 件（絞り込みと全件照合の出力一致、4 スレッドと 1 スレッドの出力一致、記憶域の上限、
並列時を含む確保失敗）、`RUFIO_TEST_FUZZY_LIBRARY` を指定した Ruby / Zig の一致テスト（絞り込み中の `scanned` も一致）、
4 万件でのスレッド照合と Ruby の一致を確認した。全 8 プラットフォームを再ビルドし、全 1,520 テストが通過した。

### 結果

| 検索語 | 改善前 rufio | 改善後 rufio | fzf |
|---|---:|---:|---:|
| `s` | 23.5ms | 9.9ms | 23.4ms |
| `sc` | 40.4ms | 12.9ms | 36.3ms |
| `sctrl` | 47.6ms | 10.0ms | 12.0ms |
| `search_controller` | 24.5ms | 1.8ms | 12.1ms |
| `xyzmissing` | 20.7ms | 1.7ms | 13.0ms |

|---|---:|---:|---:|---:|---:|
| 改善前 rufio | 22.0 | 40.0 | 50.7 | 55.1 | 47.6 |

## 追加の高速化・省メモリ化の調査（2026-11-15、未実装）

同じ条件（Apple M3、168,785 件、改善後の同梱バイナリ）で計測した。コードは変更していない。

### Ractor

キャッシュの展開（1 スレッド 51ms）を Ractor 2 / 4 / 8 個に分けると 137 / 150 / 153ms で、かえって遅くなった。
共有可能な塊への分割と 16.8 万オブジェクトへの `make_shareable` が並列化の効果を上回る。
Fiddle はメイン以外の Ractor から呼ぶと `Ractor::UnsafeError` になるため、列挙・インデックスも Ractor に移せない。
Ruby 2.7 には Ractor がない。Fiddle の呼び出しは GVL を外すので、Zig の処理はすでに Ruby と並行して動いている。採用しない。

### 内訳

- 照合（Zig 単体、上位 1,000 件）: 1 / 2 / 4 / 6 / 8 スレッドで `sc` が 53.1 / 27.7 / 16.1 / 13.1 / 12.3ms。
  照合は CPU 律速なので、コンテンツ検索（性能コア数が最速）と違い 8 スレッドが最速。既定（CPU 数）のままでよい。
- キャッシュからの再表示（0.22〜0.32 秒）: 展開 106ms、セッションの候補確認 73ms、登録 68ms（うち join 17ms）とほぼ Ruby。
- 初回の走査（約 0.5 秒）: Zig だけの列挙は約 0.25 秒。残りは Ruby の文字列・候補の作成。
- メモリ: セッションが持つ Ruby の候補 61.3MiB（Hash 25.8 + 文字列 35.5、1 件約 380B）、
  Zig インデックス 23.1MiB（`storageBytes`）、キャッシュ 13.8MiB。

### 改善案

1. **候補の Ruby 行を全件作らない**: 連結文字列とオフセットだけを持ち、上位の結果だけ行を作る。
   試作では再表示 34ms（登録 12ms・オフセット作成 12ms・照合 9ms・上位 1,000 行 0.2ms）、Ruby 側は約 15MiB。
   rga の行番号・G のブックマークなど候補ごとの情報を持つ仕組みの作り直しが必要。
2. **Zig 内で列挙からインデックス登録まで行う**: Ruby の文字列を作らず、初回の走査を Zig 列挙の約 0.25 秒に近づける。FFI 追加と再ビルドが必要。
3. **テキストの前方圧縮**: 並べ替え後の前方圧縮で 13.5MiB → 3.1MiB（試算）。照合時の復元と実装の複雑さから優先度は低い。
